# M6 连接状态与诊断修订

日期：2026-10-29；版本：0.7.1。

## 实际问题与当前状态

用户反馈：插件设置显示“ChatGPT 已连接”并取得模型，侧栏发送后提示到网页完成验证，无法收到回答。用户进一步确认同一账号在 ChatGPT 官网上可以正常聊天。

0.7.0 的“已连接”实际只检查了登录和模型列表。所有 HTTP 403，以及部分非 JSON 响应都被解释为验证要求；发送失败没有清除设置里的成功显示。旧版截图无法区分这些分支，实际失败阶段与 HTTP 状态尚未取得。

本轮尝试连接用户 Chrome 进行现场排查，浏览器连接连续失败，未能读取现场响应。没有读取浏览器凭据、Cookie 数据库或运行账号调用。**本次完成状态与诊断修复，真实账号对话尚未恢复。**

## 已修改

- 分开记录登录状态与对话状态：未验证、最近一次成功、最近一次失败。登录检查无法将对话标为成功，只有完整回答完成才可标记成功。
- 生成失败立即同步到侧栏及设置缓存，保留仍有效的登录和模型信息。返回设置时只读取后台缓存，不额外联系 ChatGPT。
- 普通 HTTP 403 显示网页拒绝请求；只有明确且已知的结构化错误码才提示验证、模型不可用或额度限制。未知 400/404/422 归为接口格式问题，不诱导反复切模型。
- 诊断保留固定失败阶段、HTTP 状态与允许分类；HTTP 200 的不兼容响应也可明确显示。原始服务器正文、自由文本错误、请求头和凭据不离开内容脚本。
- 新增“复制连接诊断”，只复制版本、连接方式、登录布尔值、对话状态及安全失败字段。排除账号、模型、问题、回答和原始响应。
- 保留每次手动发送最多一次对话请求，不自动重试或改用 API Key。状态为失败时仍允许用户明确再试；重新检查登录只回到对话未验证。

## 下一步所需信息

1. 使用本项目最新 `dist`，在 `chrome://extensions` 重新加载插件。
2. 刷新 ChatGPT 标签页，重新打开侧栏，检查登录和模型。
3. 明确发送一次简短问题。失败后返回“设置 → 侧栏对话连接”，点击“复制连接诊断”，把文字反馈过来。

无需提供账号、Key、Cookie、登录凭据或原始网络响应。取得真实失败阶段和分类后，再针对当前发送协议继续修复。

安装包：[reading-assistant-0.7.1.zip](../release/reading-assistant-0.7.1.zip)。

## 2026-10-29 后续现场信息

用户已提供 0.7.1 安全诊断：`state=ready`、`loggedIn=true`、`generation=blocked`，失败为 `conversation / HTTP 403 / accessDenied`。现在可以确认对话 POST 被拒绝；该分类没有给出服务器拒绝的具体原因，仍不能据此认定验证码、额度、模型退役或账号失效。

Codex Chrome 连接已恢复，可以访问普通 HTTPS 页面。工具拒绝认领 `chrome://extensions` 页面，并明确禁止访问 `chrome-extension://` 协议，因此没有通过其他浏览器接口绕行读取扩展内部页。

已在单独打开的 ChatGPT 官网首页观察到输入控件为 `DIV[contenteditable=true][role=textbox]`，可访问名称为“询问 ChatGPT”，该控件没有 ID。页面可以正常加载；本轮没有发送额外模型请求，没有读取凭据或既有对话正文。此信息可用于后续评估正常官网页面交互方案，尚未实现新的发送通路。

关于模型来源：插件没有硬编码 `gpt-5.6-sol`。当前 UI 优先保留已保存且仍在返回列表中的模型，否则浏览器下拉框默认选择列表首项。此逻辑没有识别官方推荐的默认模型。用户本机 Codex 全局 `config.toml` 的模型字段为 `gpt-6.1-sol`，与阅窗选择分别管理。

## 授权后的官网实测与已确认缺口

同日，用户明确授权在官网发送一句“连接诊断测试，请只回复：连接测试成功。”。通过官网可见输入框和发送按钮提交后，实际收到“连接测试成功。”。没有重放私有请求、构造校验凭证、求解验证挑战或发送额外测试轮次。

本轮只在该独立 HTTPS 测试页观察网络元信息，归档请求路径、请求头名称、请求体字段名称、公开模型名以及响应状态／类型；不保留请求头值、认证凭据、Cookie、账号信息或既有对话正文。证据见 [官网响应截图](验收证据/0.7.1/live-official-2026-10-29.jpg)与[脱敏请求结构](验收证据/0.7.1/live-official-request-shapes-2026-10-29.json)。

| 项目 | 当前官网实际测试 | 阅窗 0.7.1 |
| --- | --- | --- |
| 对话 POST | `/backend-api/f/conversation`，HTTP 200 / SSE | `/backend-api/conversation`，用户反馈 HTTP 403 |
| 网页请求校验 | 包含 Sentinel Chat-Requirements、Proof、Turnstile 请求头；观察到 prepare/finalize 流程 | 未实现前置校验，仅发送 Bearer / Accept / Content-Type |
| 客户端信息 | 包含设备、语言、client_prepare_state 等字段 | 未完整适配 |
| 本次模型 | `gpt-6-thinking` | 沿用插件所存模型；未跟随官网当前选择 |
| 可见结果 | “连接测试成功。” | 没有真实成功回答 |

由此确认实现存在关键缺口：旧接口与简化发送流程没有适配当前官网协议。缺少网页校验是 403 的高概率原因；尚未取得插件那次响应的具体拒绝规则，不能将某个请求头宣称为已独立证实的唯一触发点。该结论同时有当前官网实测和 Sider 静态代码对照支持。

Sider 5.35.3 的 `background.js` 中，发送器在字符偏移 869041 开始等待前置校验结果，873865 组装 Sentinel 相关请求头，874167 才发送 conversation；仅比较现有 session 获取代码不足以证明已经接通网页对话。

本轮只完成原因定位，没有发布新的修复包。网页模式仍未可用；修复需要重新设计发送通路，并以用户账号真实收到回答作为验收条件。
